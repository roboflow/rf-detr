!!! info "How the latency numbers were obtained"

    - **Latency**: the end-to-end `RFDETRInference.predict` call (preprocessing, forward pass and postprocessing) at batch 1, timed once for each of 500 distinct COCO val2017 images after 20 warm-up calls, with the [latency cookbook](../../../cookbooks/measure-latency/). Every export is a static batch-1 artifact.
    - **Apple Silicon configurations**: PyTorch with inductor in FP32 and FP16, PyTorch with TorchScript in FP16, and CoreML in FP32 and FP16 with two sets of compute units. PyTorch TorchScript is the traced model that `model.inference()` builds with `compile_backend="torchscript"`. CoreML uses the default `device="auto"`, which lets Core ML plan work on the Neural Engine, and CoreML GPU loads the same package with `device="cpu_and_gpu"`. No INT8 configuration is measured on Apple Silicon, because the Core ML export has no INT8 option.
    - **NVIDIA configurations**: PyTorch CUDA graph FP16 is `model.inference()` with fp16 and a captured CUDA graph. TensorRT FP16 and INT8 are static engines from `RFDETR.export(format="tensorrt")`, loaded by `RFDETRInference`, and *graph* replays the same engine as a CUDA graph through the `cuda_graph` runtime option. The INT8 engines are calibrated on 128 train2017 images. Atto, Femto and Pico have no INT8 configuration, because they lose 7.0 to 8.7 AP in TensorRT INT8 and a faster artifact is not a usable answer when its accuracy is not acceptable.
    - **Apple run**: Apple M4 Max (16-core CPU, 40-core GPU), macOS 26.7.1, rfdetr 1.13.0.dev0, rfdetr_plus 1.2.0, torch 2.14.0 and coremltools 9.0, measured on 2026-11-13. Every column and every size comes from one run of the cookbook, and no other work was started on the machine while it ran. PyTorch inductor predictors are built by `model.inference()`, which holds Dynamo's recompile limit above the default of 8 and compiles with `dynamic=False`; without that, inductor predictors built after the eighth in one process run several times slower or fail to compile, as the [FAQ](../../../faq/#why-is-an-inductor-predictor-slower-after-i-built-several-models-in-one-process) explains.
    - **NVIDIA run**: Tesla T4, NVIDIA L4, A100-SXM4-40GB and RTX PRO 6000 Blackwell Server Edition, one run of the cookbook per GPU on 2026-11-13, each with rfdetr 1.13.0.dev0, rfdetr_plus 1.2.0, torch 2.14.1 (CUDA 13.0) and TensorRT 11.4.0.106. Every engine was built on the GPU that timed it. The host CPU was not recorded, and a call includes host work, so a small model on a fast GPU can be limited by the host.
    - **Ties**: on the M4 Max, repeated runs of the largest models differed by 5 to 7%, so treat a gap under about 5% to the next configuration as a tie and pick by accuracy and tooling. Each NVIDIA GPU was measured once, so its run-to-run spread is not known, and the same 5% rule is used there.

!!! warning "FP16 and INT8 can lower accuracy"

    Most of the fastest configurations above run in FP16 or INT8. The FP16 and INT8 AP in the [table above](#pre-trained-checkpoints) was scored on TensorRT engines, where FP16 stays within 0.1 AP of FP32 for every size here and INT8 costs 0.4 to 0.9 AP for the sizes timed in INT8, so read the INT8 column before you choose an INT8 engine. The AP was not scored for PyTorch CUDA graph FP16, or for PyTorch and CoreML FP16 on Apple Silicon, so check the accuracy on your own data before you rely on one of those configurations.
