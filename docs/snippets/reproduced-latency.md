!!! info "How the latency numbers were obtained"

    - **Latency**: the end-to-end `RFDETRInference.predict` call (preprocessing, forward pass and postprocessing) at batch 1, timed once for each distinct COCO val2017 image (500 on Apple Silicon and NVIDIA, 200 on the CPU, where a call is far slower) after 20 warm-up calls for the Apple run and 50 for the NVIDIA and CPU runs, with the [latency cookbook](../../../cookbooks/measure-latency/). Every export is a static batch-1 artifact.
    - **Apple Silicon configurations**: PyTorch with inductor in FP32 and FP16, PyTorch with TorchScript in FP16, and CoreML in FP32 and FP16 with two sets of compute units. PyTorch TorchScript is the traced model that `model.inference()` builds with `compile_backend="torchscript"`. CoreML uses the default `device="auto"`, which lets Core ML plan work on the Neural Engine, and CoreML GPU loads the same package with `device="cpu_and_gpu"`. No INT8 configuration is measured on Apple Silicon, because the Core ML export has no INT8 option.
    - **NVIDIA configurations**: PyTorch CUDA graph FP16 is `model.inference()` with fp16 and a captured CUDA graph. TensorRT FP16 and INT8 are static engines from `RFDETR.export(format="tensorrt")`, loaded by `RFDETRInference`, and *graph* replays the same engine as a CUDA graph through the `cuda_graph` runtime option. The INT8 engines are calibrated on 128 train2017 images. Atto, Femto and Pico have no INT8 configuration, because they lose 7.0 to 8.7 AP in TensorRT INT8 and a faster artifact is not a usable answer when its accuracy is not acceptable.
    - **Apple run**: Apple M4 Max (16-core CPU, 40-core GPU), macOS 26.7.1, measured on 2026-11-13, with the versions in the table below. Every column and every size comes from one run of the cookbook, and no other work was started on the machine while it ran. PyTorch inductor predictors are built by `model.inference()`, which holds Dynamo's recompile limit above the default of 8 and compiles with `dynamic=False`; without that, inductor predictors built after the eighth in one process run several times slower or fail to compile, as the [FAQ](../../../faq/#why-is-an-inductor-predictor-slower-after-i-built-several-models-in-one-process) explains.
    - **NVIDIA run**: Tesla T4, NVIDIA L4, A100-SXM4-40GB and RTX PRO 6000 Blackwell Server Edition, one run of the cookbook per GPU on 2026-11-13, each with the versions in the table below. Every engine was built on the GPU that timed it. The host CPU was not recorded, and a call includes host work, so a small model on a fast GPU can be limited by the host.
    - **CPU configurations**: PyTorch TorchScript in FP32 (`model.inference()` with `compile_backend="torchscript"`), ONNX Runtime in FP32 and INT8, and OpenVINO in FP32, FP16 and INT8, each exported with `RFDETR.export` and loaded by `RFDETRInference` on the CPU. Every runtime is asked for all 8 logical cores: PyTorch through `torch.set_num_threads`, ONNX Runtime and OpenVINO through the `num_threads` runtime option, with OpenVINO hyper-threading enabled. The INT8 artifacts are calibrated on 128 train2017 images. Atto, Femto and Pico have no INT8 configuration, for the reason given for NVIDIA above.
    - **CPU run**: a Colab x86 host with an AMD EPYC 7B12 and 8 logical cores, measured on 2026-11-14 in one run of the cookbook with the versions in the table below. The host is shared, and the 95th percentile reaches 2.19 times the median in the worst cell (TorchScript FP32 on keypoints).
    - **Ties**: on the M4 Max, repeated runs of the largest models differed by 5 to 7%, so treat a gap under about 5% to the next configuration as a tie and pick by accuracy and tooling. Each NVIDIA GPU and the CPU host were measured once, so their run-to-run spread is not known, and the same 5% rule is used there.

    | Run                                  | `rfdetr`    | `rfdetr_plus` | PyTorch            | Runtime packages                                                 |
    | ------------------------------------ | ----------- | ------------- | ------------------ | ---------------------------------------------------------------- |
    | Apple M4 Max                         | 1.13.0.dev0 | 1.2.0         | 2.14.0             | coremltools 9.0                                                  |
    | NVIDIA T4, L4, A100 and RTX PRO 6000 | 1.13.0.dev0 | 1.2.0         | 2.14.1 (CUDA 13.0) | TensorRT 11.4.0.106                                              |
    | x86 CPU (AMD EPYC 7B12)              | 1.13.0.dev0 | 1.2.0         | 2.14.1 (CPU build) | ONNX Runtime 1.32.0, OpenVINO 2026.4.1, NNCF 3.4.0, psutil 7.2.2 |

    The cookbook writes the installed versions of these packages into every result row, and installs the extras for its hardware: `plus,coreml`, `plus,tensorrt` or `plus,onnx,openvino` (CPU runs add `nncf` and `psutil`). The NVIDIA and CPU runs installed `rfdetr` 1.13.0.dev0 from the `docs/measure-latency-cookbook` branch archive, so no commit hash was recorded, and the Python version was recorded only for the CPU run (3.13). To reproduce a number, pin the packages above in a fresh environment and rerun the cookbook for your hardware.

!!! warning "FP16 and INT8 can lower accuracy"

    Most of the fastest configurations above run in FP16 or INT8. The FP16 and INT8 AP in the [table above](#pre-trained-checkpoints) was scored on TensorRT engines, where FP16 stays within 0.1 AP of FP32 for every size here and INT8 costs 0.4 to 0.9 AP for the sizes timed in INT8, so read the INT8 column before you choose an INT8 engine. The AP was not scored for PyTorch CUDA graph FP16, or for PyTorch and CoreML FP16 on Apple Silicon, so check the accuracy on your own data before you rely on one of those configurations. The same holds on the CPU: ONNX INT8 is the fastest configuration for 10 of the 16 models, and no AP was scored for any CPU configuration here. The [ONNX page](../../../exports/onnx/) reports that ONNX INT8 cost 2.65 mAP on Nano and 2.67 on Small in a separate 500-image check, so measure it on your own data before you choose it.
